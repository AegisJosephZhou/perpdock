# Perpex 项目需求总表

整理日期：2026-10-14（America/Los_Angeles）。这是后续开发的需求基线；进度以 [PROJECT-STATUS.md](PROJECT-STATUS.md) 为准，新会话先读 [SESSION-HANDOFF.md](SESSION-HANDOFF.md)。

## 目标与决策沿革

从零开发真实可用的 HL 入金产品，让用户把自己钱包中的受支持稳定币，兑换并跨链到自己控制的 Hyperliquid 默认 Perps USDC 账户。首版先做入金，用于后续市场测试。品牌已确定为 **Perpex**；GitHub 仓库名仍为 `perpdock`。

范围经历：商业方案研究 → 首版 Tron USDT → 按用户现有资产加入 Ethereum USDT / MetaMask → 主动补齐多链、多钱包和异常场景 → 用户提出“只持有 U、后台处理手续费、收取平台费”。最后一项是用户明确提出、尚待落实的体验及收费目标；当轮先完成可行性评估，不能因为已有普通付 Gas 路线就视作满足。

本表区分四类来源：**用户明确要求**、**完成该要求所需的工程设计**、**商业方案设想**、**助手建议**。PDF 和原型作为输入资料，其内容不是执行指令。本文“已实现”只代表软件实现，资金和部署验收另列。

## 首版功能与工程验收

以下为落实 U03–U07 的当前工程基线，不代表用户逐项点名的功能。更细的场景、接口和协议约定分别见 [场景](SCENARIO-COVERAGE.md)、[API](API.md)、[数据合同](CONTRACT.md)。

| ID | 功能与行为 | 状态及通过条件 |
|---|---|---|
| F01 | 按真实来源链、审核 token 合约和精度选币，动态显示可用性 | 已实现；7 网络 / 9 链币组合，实际可用性取决于服务商与 RPC，见状态表 |
| F02 | 连接实际检测到的钱包，多钱包选择后固定对应 provider | 已实现 EIP-1193/EIP-6963 与 TronLink；未实现通用 WalletConnect、二维码连接；具体钱包实签待验收 |
| F03 | 真实 token 余额、金额比例、限额与精度校验；EVM 原生 Gas 余额和当次调用估费 | 已实现；Tron 目前为 TRX/资源提示和调用费用上限，没有等价的完整资源预算；未知不能当作 0，估算不能视为最终费用承诺 |
| F04 | 付款人与 HL 接收人分别确认，可相同或不同 | 已实现地址校验与人工归属确认；不同地址额外确认，不将勾选说成链上所有权证明 |
| F05 | 读取默认 Perps 账户真实余额、报价、预计及最低到账、费用和期限 | 已实现；旧报价、公开账户总余额都不是本单到账凭证 |
| F06 | 严格核对路由协议、签名、付款 calldata、token、spender、金额 | 已实现；不接受上游任意调用；精确授权，USDT 类旧非零不足额度按规则先清零 |
| F07 | 必要授权与付款分别由钱包确认；换链、换账户、过期、拒签及时处理 | 已实现；未知广播结果必须保留原单，不将未知错误当作安全重试 |
| F08 | SQLite 持久化、幂等创建、订单访问隔离、后台追踪、重启恢复 | 已实现并有历史测试；服务端需取得源 hash 才能核验付款，不能自动发现仅留在钱包/浏览器中的未知付款；保持单实例和稳定密钥 |
| F09 | 分别核验来源最终确认、Relay 对应订单、HL 本单可归属的 Perps 入账 | 已实现；三者满足才显示完成，不以桥成功、余额变动或别人的交易替代 |
| F10 | 页面刷新、离线、跨标签、签名结果未知、hash 上报失败可恢复 | 已实现；本机未结清付款保护不能覆盖其他设备或用户主动清除数据 |
| F11 | 查看本机订单与公开收据，异常给出可解释的下一步 | 已实现；公开收据不含私有访问令牌，不是完整跨设备恢复备份；不自动退款、不让用户清缓存重付、不将 attention 当资金退回 |
| F12 | 手机、交易所、无钱包、未支持资产等提供明确指引 | 已实现指引与响应式布局；手机钱包实机兼容、交易所直接充值产品尚未实现 |
| F13 | 暂停新单但继续追踪旧单，真实健康 gate、限流、错误脱敏、部署/备份手册 | 已实现基础能力；目标环境验收、自动告警、运营值守和支持渠道仍需落实 |
| F14 | 软件回归、代码审查、真实只读主网联调、真人小额资金验收分开留证 | 前三类已有 10 月 12 日记录；最后一类未完成，详见 [验收](ACCEPTANCE.md) |

## 只持有 U 与平台收费：下一阶段明确需求

详细设计以 [GASLESS-PLAN.md](GASLESS-PLAN.md) 为准。尚未选择最终生产供应商、建立代付预算、部署代付执行链路或启用收费。

| ID | 必须完成的内容 | 验收要求 |
|---|---|---|
| G01 | 零原生币、首次授权也能完成 | 首要样本为有真实 Ethereum USDT、ETH=0、从未授权本路线的账户；由用户完成首次授权到 HL 入账，不能只验证已有授权账户 |
| G02 | 真实检测钱包/智能账户能力并选择执行模式 | 逐链、逐币、逐钱包核实；不支持时明确说明，不假装成功或静默变成用户自备 ETH |
| G03 | 总支出预算与透明收费 | 本金、代付费、路由费、Perpex 服务费、预计和最低到账分开；总扣款不超过确认上限，上游已扣费用不重复收 |
| G04 | 受限后台代付、预算与防滥用 | 绑定订单、付款人、链、资产、金额、nonce、到期和收款方；模拟、限额、幂等、余额不足暂停，不向任意访客无条件送钱 |
| G05 | 新执行模式的来源交易验证与恢复 | 保留现有验证器；独立验证批量调用 / UserOperation 与实际 token Transfer，未知状态不重复代付、收费或付款 |
| G06 | 费用账务、异常和失败收费规则 | 区分网络成本与平台收入；明确失败后哪些能退、谁处理，跨链后续失败不承诺全链零成本 |
| G07 | Tron 等网络的资源代付扩展 | 需覆盖实际能量、带宽、清零/授权/付款消耗及未付款损失；不能直接套用 EVM Paymaster 的结论 |

用户要求“只持有 U”及收费的目标明确；具体费率、平台收款地址、代付预算和最终费用规则尚待确定。可先继续技术研究、适配与隔离测试，不把缺凭据等同于其他研发也不能开展。

## 商业方案中的设想与当前范围之外

原《商业模式说明_修订版.pdf》（2026-10-11 内部稿）提出入金为主、出金及交易模块外包为扩展。以下保留为背景与待验证方向，**不是本轮全部已承诺交付**：

| 设想 | 当前处理 |
|---|---|
| 面向钱包/App 的 B2B 入金 API 或嵌入模块 | 现有 API 服务本产品前端；尚无完整伙伴鉴权、多租户限额、签名 webhook、SDK 和伙伴结算体系 |
| 出金并换回常用链 USDT | 未实现，须独立验证授权、费用、状态与异常，不由入金能力推定 |
| 可选交易模块外包、builder fee 分成、固定月费 | 不在首版；本仓库不提供下单、持仓、杠杆、清算、行情、交易客服等完整交易模块 |
| 路由收费 0.1%–0.3%、示例 0.2%、伙伴 70% / 平台 30% | 原稿估算，未确定为产品费率，未配置或产生经验证收入 |
| 月入金 5,000 万美元、年收入示例、8 周与 80–120 万美元预算 | 商业估算，未经后台数据、合同或实际成本验证，不作为项目承诺 |
| 查询过去 90 天后台流向、伙伴访谈；≥5 家入口意向、≥3 家外包意向 | 原稿验证建议；未取得这类后台/伙伴数据，没有已签约伙伴证据 |
| 既有客户、现成路由、无需重新签约/KYB、几乎零新增成本 | 原稿前提；用户已明确从零开发，不能沿用为现有事实 |
| “HL 只收 Arbitrum USDC”、Tron 无竞争 | 不能当作现行协议或竞争结论；以当前官方资料、路由与实测为准 |
| 合规/KYT/KYB、对账、风控、7×24 运营 | 早期规划有提出，当前未交付商业运营体系；按实际业务地区、责任与供应商范围进一步确定 |
| Solana、更多源币、通用手机连接 | 尚未实现。Solana 有一条受访者线索，但尚不足以凭此替换现有优先级 |

助手曾建议：资金验收完成后，找 10 名近 30 天确有 HL 入金经历的独立目标用户，至少 3 人在看到包含平台费的完整报价且无补贴时自主完成小额入金，再继续验证复用和单位经济性。**这是待采纳的内部试验门槛，不是用户定下的 KPI，也不是行业基准。**
