# 产品与交付研究备忘录

供主报告整合。依据：`work/pdf/source.txt` 的两页商业方案；截至本备忘录，未拿到现有代码、API、后台数据、合同、人员名单或供应商报价。以下范围、资源和排期均为研究建议，不代表现有能力或承诺。根代理已同步官方资料核验：HL 当前推荐 CCTP，旧 Arbitrum bridge 已弃用；Circle 覆盖 HyperEVM 但不覆盖 Tron；deBridge 已支持 Tron。因此不能以“只新增一个旧桥目的地”或“Tron 无竞争”为立项依据。

## 1. 立项顺序与交付目标

建议分成三个可独立批准、可独立终止的项目包：

1. **A：HL 入金试点。** 先限定一种源资产、一条源链、明确支持的钱包及用户地址类型，做 Tron USDT → 用户确认的 HL 账户入金。最终路线必须用最新官方文档和实际测试确认，包含从受支持链的 USDC/CCTP 到 HL 账户可用保证金的完整过程。技术价值是可靠报价、透明收费、资金追踪和异常处理；商业价值要通过真实伙伴需求与报价比较验证。
2. **B：HL 出金。** 单独交付反向链路、提现状态、源端与目的端费用、地址校验、库存/流动性以及资金异常处理。能入金不等于能可靠出金，不与 A 共用一个含糊的“2–4 周完成”承诺。
3. **C：PerpDock 外包交易模块。** 入金试点验证后再依据独立需求与商业承诺立项。交易、行情、账户状态、builder 授权与分成，以及支持运营属于额外系统；不应拖慢 A。

建议 A 先做小规模、白名单、限额试点。报价页面可提供统一入口，但跨链过程通常包含多个授权、签名、兑换和结算步骤。“一键”应解释为产品入口和流程整合，不能暗示一笔原子交易或无条件即时到账。

## 2. 用户、伙伴和运营旅程

| 角色 | 完整旅程 | 产品必须提供的证据 |
|---|---|---|
| 终端用户 | 在伙伴 App 选择“存入 HL” → 选择源钱包/金额 → 绑定并确认目的 HL 地址 → 阅读预计到账金额、全部费用、时间及风险 → 按钱包要求授权/签名 → 查看进度 → HL 保证金可用，或进入可解释的恢复流程 | 地址核验结果、报价有效期、需签名次数、源交易/中间步骤/最终到账凭证、费用收据、客服订单号 |
| 伙伴开发者 | 获取集成说明/测试凭据 → 请求报价和创建入金意图 → 嵌入钱包签名 → 查询订单或接收 webhook → 处理重试/错误 → 沙盒验证 → 小流量试点 → 对账 | 版本化 API、示例、错误码、签名 webhook、幂等规则、状态定义、对账记录、支持联系方式 |
| 伙伴运营/财务 | 配置可用链与限额/费率 → 查看成交和失败漏斗 → 处理客户咨询 → 核对手续费和分成 → 确认结算 | 订单检索、审计日志、收入/成本/退款明细、待处理资金清单、结算周期和差异处理规则 |
| 平台运营/风控 | 监控通道/供应商/余额 → 拦截不满足规则的报价或资金流 → 发现超时/失败 → 追踪资金位置 → 执行有权限控制的恢复/退款 → 复核关单 | 告警、订单与资金台账、异常责任人、操作手册、双人复核的高风险操作、停用链路与暂停新订单能力 |

Tron 地址和 EVM/HL 地址不是天然同一个地址。跨钱包、交易所来源地址、合约钱包与代理钱包是否支持，应逐类确认。地址归属及用户授权测试必须先于展示“自动识别你的 HL 地址”。

## 3. A 项目的 MVP 范围

### In

- 一个优先链路：Tron 上的明确 USDT 合约 → 经已验证的兑换/跨链服务 → HL 账户可用保证金。只支持白名单资产、链和已验证的地址类型。
- 报价与路由筛选：总输入、预计输出、最低可接受输出或价格保护、平台费/供应商费/链上费、报价到期规则、路由提供方及预计时间。
- 订单编排：报价、入金意图、签名/付款、执行、步骤追踪、终态确认；重复点击、断网、刷新后可恢复。
- 伙伴 API、简易参考界面或可嵌入组件、开发者文档、webhook/查询状态、伙伴维度的权限和限额。
- 订单/费用/资金台账及对账；能定位每笔资金最后确认的位置。不能只依靠一个跨链交易哈希。
- 失败恢复：收款前失败、已兑换未跨链、已跨链未形成 HL 可用余额、长时间不确定、不可自动恢复等分类；必要时进入人工队列。
- 安全、KYT/KYB 接口和发布控制按实际责任边界接入；运营人员看得到未结案资金和处置期限。
- 小规模 mainnet 验证、伙伴试接、有限流量试点、发布和事件处置手册。

### Out

- “任意链任意资产”；先不默认加入 BSC、Solana、全部 EVM 链。
- 出金、自动返程兑换及所有资产的退款保证。
- 自研桥、自研兑换池、自营做市和为了赶工自行承担未知的资金托管职责。
- PerpDock 的下单、杠杆、清算、行情与交易客服。
- 完整白标 App、通用钱包、AI 客服自动处理资金操作、多交易所接入、策略/跟单。
- 无限额开放公测、未经验证的“零成本”“不重新签合同/KYB”“全程非托管”等对外表述。

## 4. 用户故事与验收标准

以下标准是研发验收建议，需在第 1 周评审后冻结数值指标。现阶段不编造到账时延、成功率和经济性数字。

| 编号 | 用户故事 | 核心验收标准 |
|---|---|---|
| A01 | 用户能清楚知道将花多少钱、收到多少 | 下单前展示完整费用和预期到账；过期报价不可静默沿用；低于有效最低金额、资产不匹配和不支持链均在执行前拦截；最终扣费与报价承诺可核对 |
| A02 | 用户可确认资金进入自己指定的 HL 账户 | 源地址与目的地址分别展示并验证；需要何种归属证明由地址模型确定；错误网络/格式/不支持账户类型均有明确处理；无证据时不宣称地址归属已验证 |
| A03 | 用户重复点击或网络重试不导致重复执行 | 相同幂等意图不会生成重复支付指令或重复执行；新意图与既有意图区分明确；刷新、签名拒绝、钱包切换、重连有可复现测试 |
| A04 | 用户能知道钱在哪、下一步是什么 | 状态页可恢复；不把“源交易确认”或“桥交易完成”当成最终入账；只有目的账户入账证据满足规则才显示完成；延迟/未知状态可解释并有支持入口 |
| A05 | 一段成功、一段失败仍能被处理 | 在每个关键步骤注入超时、失败、重复回调和进程重启；资金最后位置可查；可重试条件、恢复权限、退款条件和不可恢复情况均有 runbook；异常单不可被错误归档 |
| A06 | 伙伴可以可靠集成 | 文档、测试环境、API 错误码齐全；webhook 有身份校验、重试及重复/乱序消费方案；伙伴隔离经测试；一个独立开发者能依文档完成参考流程 |
| A07 | 财务能核对每笔费用与资金 | 实测每个订单有资金和手续费明细；费用口径明确区分毛收入、供应商成本、Gas、退款和伙伴分成；完成交易与台账可核对，差异可解释且有人处理 |
| A08 | 运营可以及时停用坏通道 | 可按链、供应商、伙伴暂停新订单；在途订单仍可追踪和恢复；演练供应商故障、余额不足、目的场所不可用与告警升级 |
| A09 | 安全边界可以审查 | 不接受用户私钥；交易授权内容与权限符合设计；生产密钥、管理权限和敏感操作可审计；独立安全评审的阻断项关闭后才开启资金试点 |

关键度量必须同时记录定义和分母：已报价→已付款→已执行→最终到账的漏斗；资金已进入流程后的完成率及超时率；端到端 p50/p95；每条路由毛收入/供应商成本/Gas/退款损失/支持成本；未结案资金笔数、金额和账龄。超时和人工处理中订单不可从成功率分母悄悄剔除。

## 5. 双路径排期：先识别能复用什么

### 路径 A：可复用成熟路由及运营能力

**必须同时成立的前提：**

- 已有可生产使用的 Tron USDT 接入、兑换、跨链与流动性供应；相关 API、合约和商业许可可用。
- 已有伙伴鉴权、计费、KYB/KYT、订单台账、对账、异常处理、监控、值班与资金运营。
- 已明确支持的 HL 地址类型，能将当前推荐入金机制完整接入至 HL 可用余额；旧桥迁移影响已排除。
- 供应商支持目标路径，费用与限制已验证；不需新建桥/资金托管系统，也不需等待数周的供应商准入。
- 产品只做窄范围入金试点；安全评审与测试资源能及时排期。

| 阶段 | 时间参考 | 产出与门槛 |
|---|---|---|
| 可行性研究 | 第 1 周 | 代码/API 能力清单、路由对比、地址与资金异常 PoC、商业样本、范围冻结；形成继续/缩小/停止决定 |
| HL 适配和集成 | 第 2–4 周 | 当前 HL 入金适配、状态与账务补齐、伙伴 API/参考流程，沙盒端到端通过 |
| 安全/故障验证与试点 | 第 5–6 周 | 故障注入、对账演练、独立安全评审、小额 mainnet、1–2 家设计伙伴试点 |
| 受控推广 | 第 7–8 周，按证据决定 | 真实订单稳定、未结资金受控、伙伴准备就绪、单笔经济性可接受后逐步扩大 |

原文“2–4 周”可以作为**前提已满足以后，窄范围适配或技术 beta 的候选窗口**。对外部真实资金和伙伴服务的交付基准，建议采用上表的 6–8 周研究、开发、加固与受控试点节奏。商务等待、安全评审排队及超出假设的改造必须另外计算。不能直接承诺入金+出金+全天运营在第 4 周完成。

建议能力配置：后端/路由工程 2 FTE，前端/SDK 0.5–1，QA 0.5–1，SRE/安全合计 0.5–1，产品/交付 0.5；合计约 4–5.5 FTE。法务、风控、财务、现有值班是必要共享依赖。此为能力覆盖，不等于已有人选。

### 路径 B：从零做产品系统，外部采购兑换/跨链能力

如果没有现成路由、账务和运营平台，必须先建设编排、伙伴接口、监控、对账、异常处理等基础系统，不能套用“只加目的地”。

| 阶段 | 时间参考 | 产出 |
|---|---|---|
| 发现与供应商验证 | 第 1–2 周 | 明确资金模型、路由PoC、合作条款/成本、需求与安全威胁模型 |
| 平台基础 | 第 3–6 周 | 订单状态机、伙伴鉴权、账务/对账、密钥与环境、风控接点、基础监控 |
| 端到端入金和加固 | 第 7–10 周 | 钱包流程、供应商集成、HL 入金确认、参考组件、运营控制台、故障恢复和安全验证 |
| 试点 | 第 11–14 周 | 独立安全审查通过、压测/对账、有限资金试点、运营演练 |

**12–14 周仅为当前阶段的规划区间**，从必要人员到位、供应商可访问及资金/合规模型确定后计算；若采购、审计、地区许可或资金安排未完成，日历工期顺延。建议 6–8 FTE 核心交付能力：后端/路由 2–3、前端/SDK 1、QA 1、SRE 0.5–1、产品/技术负责人 1、安全 0.5；部分角色可兼任，关键审查必须保持独立。

若“从零”还要求自研桥、流动性、托管或风险引擎，则已是另一个高依赖项目，不应在当前资料下给出可信上线日期；需先完成专项可行性、安全与运营设计再估算。供应商退出、权限限制和支付责任也应进入选型条件。

### B：出金的后续参考

在 A 稳定且确认实际提现 API、目的链供应、授权与资金责任后，预留额外 2–4 周的适配及试点窗口；这不是已验证工期。提现冷却/延迟、费用、流动性、地址归属、失败返还与入金完全不同。若依赖新增供应商或系统，则重新估算。

## 6. PerpDock 的八周前提与独立范围

八周可以讨论的对象应是“已有钱包/伙伴 App 上的窄范围交易 beta”，且以下条件先满足：伙伴已经选定并配合；成熟 HL 交易接口和 SDK 可用；交易签名、agent/builder 授权、账户模型已验证；数据服务和组件有可复用基础；法务及运营责任可落实；安全审查资源已预订。

可纳入：单一场所行情/市场列表、基本下单与撤单、持仓/挂单/余额和风险提示、明确支持的基本订单类型、连接中断恢复、授权管理、费用/分成记录、支持工单与人工值班接口。止盈止损、杠杆调整等必须逐项验证支持的真实语义并加入验收，不可笼统写“交易全功能”。

排除：自研清算/风险引擎、跨场所保证金、跟单、自动策略、收益保证、平台替伙伴承担一切监管义务、AI 自动决定补偿或执行资金操作。

候选八周结构：第 1–2 周账户/授权/交易适配与风险设计；第 3–4 周交易界面与账户状态；第 5–6 周故障恢复、分成/支持工具和伙伴联调；第 7–8 周安全评审、模拟和小额资金验证、白名单 beta。若这些前提需在八周内从零补齐，应改为先做 2 周技术发现，再给承诺日期。

候选团队：技术负责人/后端 1、交易/账户后端 2、前端/SDK 2、QA 1–1.5、SRE 0.5–1、产品 0.5–1、安全共享 0.5，约 7.5–9 FTE 能力覆盖。人员规模不能代替外部依赖，也不能保证八周压缩成功。

## 7. 预算与“80–120 万美元”的审查

没有工作分解、人员费率、供应商报价和服务承诺，原文数字只能当待验证的投资预算，不能当工程成本估算。

建议预算表分开列：

1. 一次性开发：各工作包的角色 × FTE × 周数 × 含管理成本的周单价。
2. 一次性外部费用：安全审计、法律评审、供应商接入、测试资金与演练费用。
3. 上线后月度成本：RPC/索引/监控、供应商固定费用、KYT、客服、工程值班、财务与对账。
4. 按交易变动成本：兑换点差、跨链服务、Gas、失败成本、分成与退款损失。
5. 资金需求：库存/预充值/保证金与风险准备金。这些不能混同为已消耗的开发费用。
6. 风险预留：仅基于已识别的风险及发生概率列示，不用一个大额缓冲掩盖未知范围。

数量级交叉检查：若 8 周约等于 2 个月，平均团队 7–9 FTE，则为 14–18 人月。若 80–120 万美元全部解释为研发人力，则隐含每人月约 4.4–8.6 万美元。此计算不代表市场薪酬；它提示必须解释预算中审计、运营、库存、外包利润和风险预留的占比。用实际团队报价替换后才能下结论。

入金年收入 120 万美元只是 `5000 万美元/月 × 0.2% × 12` 的毛收入算式。应以同口径、同金额、同时间的供应商报价评估净收益；入金与出金量、重复周转量和独立用户数须分开，不能同一笔钱反复流动就暗示新增需求。

| 地址与资金异常 PoC | 后端 + 安全 + QA | 沙盒/测试资金、授权的钱包、当前官方接口 | 源/目的地址绑定、HL 入账证据、超时与部分失败的最小验证；记录每一步资金位置 | 决定资金模型是否可交付 |
| 90 天需求分析 | 数据 + 产品 | 经授权的脱敏订单、源链/资产、路线、金额、费用与状态数据 | 源资产/链分布、可归因 HL 流量、样本置信度、Tron 占比、失败和费用分布 | 估计真实需求与可服务人群 |
| 伙伴研究准备 | 产品 + 商务 | 已有伙伴清单和渠道授权 | 访谈问卷、样本分层、集成成本假设、设计伙伴选择标准；若另有明确授权再执行触达 | 验证“愿意接”及真实外包需求 |
| 范围/预算评审 | 产品 + 工程 + 安全/风控/财务 | 上述结果 | PRD v0.1、状态/数据模型、范围冻结单、测试与上线门槛、估算上下界和剩余未知项 | 第 5 个工作日作继续/缩小/停止决定 |

目前的“研究启动”可直接完成文档分析、公开资料核验、架构/需求拆解和验证计划。没有后台权限或测试环境时，把证据需求清楚列出；不能报告“已完成 90 天后台分析”或“已联系 5 家伙伴”。

HL 归因应标注直接、间接和未知三类证据。只看最终桥合约收款不一定能证明资金来自某个原始用户，更不能把旧桥数据当作当前全部入金量；需要根据最新链路和多跳转移做可解释归因。

## 9. 决策门槛与责任

- 原文“≥5 家愿意添加入口”“≥3 家想外包”是提案商业门槛。它们不是已发生事实，也不是要求代理立刻联系伙伴的用户命令。
- 建议把意向升级成有证据的承诺：具体负责人、技术接入路径、预期月流量/活跃用户、上线时间、支持区域、费用接受度；口头兴趣和签署试点需分开记录。
- 达到商业数量门槛不自动允许上线。另需技术可行、安全审查、责任边界、实际路由经济性和运营准备五项独立放行。
- 入金试点先由 1–2 家设计伙伴验证可用性；是否达到五家作为扩大投入的商业判断，不能为了凑数阻止低成本研究，也不能以数量替代真实使用。
- 外包模块的运营 SLA 和法律责任必须写入实际协议。产品里有工单/风险披露不等于责任已被转移。
- 任命单一交付负责人维护范围、依赖、风险和发布决定；每个工作包有明确负责人；安全与财务各自拥有其放行项，商业负责人不能单独覆盖。

## 10. 给主报告的简短结论

推荐第一周先验证“现有路由可复用程度、当前 HL 入金全链路、Tron 路由竞争力、真实伙伴需求”四件事。成功后按小范围入金 beta 执行；出金和 PerpDock 独立排期。原文 2–4 周、八周和 80–120 万美元不能直接成为承诺：只有工作范围、现有能力、供应商/安全依赖、资金模型与实际报价明确后才可冻结。
