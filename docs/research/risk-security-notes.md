# HL 入金 + 可选 PerpDock：安全、风控与质量研究

研究日期：2026-10-12。输入：商业模式说明修订版两页、当前可读取官方技术资料。此稿是开发研究建议，不是法律意见、安全审计结论或已完成的验证报告；未访问企业后台、供应商合同、生产系统或用户资金，也未执行交易。

## 一、立即影响开发方案的事实修订

1. **不能将“HL 只收 Arbitrum USDC”作为架构前提。** HL 当前开发文档将 CCTP 列为首选，并将旧 Arbitrum Bridge 标为 deprecated。旧桥说明中的 5 USDC 最低额、发送者记账规则只适用于旧桥，不能套用新路线。[HL USDC 开发文档](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/usdc)
2. **Tron 段没有被 CCTP 自动解决。** 当前 Circle CCTP 支持域表包含 HyperEVM，未列 Tron；因此本产品仍需证明 Tron USDT → 支持链原生 USDC 的兑换、流动性和结算能力。不要把“USDT 可发送”和“CCTP 可桥接 USDC”拼成未经验证的一条路线。[Circle 支持域](https://developers.circle.com/cctp/concepts/supported-chains-and-domains)
3. **到账目标必须是 HyperCore 的正确用户与账户，而非只到 HyperEVM。** Circle 文档解释 HyperCore 显示协议层余额，原生 USDC 留在 HyperEVM 的 CoreDepositWallet。其文档描述新路线没有最低入金额，并描述新户 1 USDC 激活费；但团队发现 HL 与 Circle 对激活扣费时点的官方口径可能不同，**金额可用性、扣费时点及最低可完成入金额列为 PoC/协议确认项，报价使用可配置费用预留**，不能据某一页直接许诺用户可用余额。测试网收款地址须已有主网状态，并有测试余额限制，不能将该行为误判成集成失败。[Circle HyperCore 流程](https://developers.circle.com/cctp/concepts/cctp-on-hypercore)
4. **不可将普通 token transfer 当入金。** CoreDepositWallet 要调用 deposit/depositFor/depositWithAuth；直接向该合约转币不会触发 HyperCore 入账，官方明确资金会永久卡住。depositFor 支持由付款方为指定 HyperCore 收款者入金。[CoreDepositWallet 接口](https://developers.circle.com/cctp/references/coredepositwallet-contract-interface)
5. **代付 gas 的签名不是直接照搬自付 gas 示例。** Circle 的 CctpExtensionV2 将授权 nonce 绑定完整存款参数，防止 relayer 改收款方或费用；批量调用可能逐条 skip，整笔交易成功不能代表每个订单都成功。[Circle V2 代付流程](https://developers.circle.com/cctp/howtos/transfer-usdc-from-arbitrum-to-hypercore-with-cctp-extension-v2)
6. **KYB 与责任必须重评。** Circle 当前 Developer Terms / Permissionless Product Schedule 要求接入方对自有服务、相关法律和安全负责；permissionless 不是责任转移。[Circle 开发者条款](https://console.circle.com/legal/developer-terms)

## 二、上线前必须定下的控制边界

| 边界 | 待做的具体决定 | 建议验收证据 |
|---|---|---|
| 用户 Tron 钱包 | 用户自己签 source transfer；平台不得收集助记词或主私钥 | 钱包兼容矩阵、签名可读展示、实际合约/金额/收款地址断言 |
| Tron→USDC 兑换 | 是用户与供应商直结、平台代收再兑换，还是供应商代收？谁在每一刻能转走资产？ | 每跳资金流图、控制私钥主体、合同、退款主体、破产/冻结时的权利 |
| 流动性 | 供应商现货换汇、预存 USDC 库存、平台垫资分别占多少；谁承担汇差和延迟 | 真实可执行报价、余额/限额、补库存演练、成本分解 |
| 中间链 USDC | 持有者为用户、供应商还是平台钱包；不可把中间保管称作“全程非托管” | 每跳地址白名单及资金归属台账 |
| CCTP 与 HyperCore | 谁发 burn、谁支付 gas、谁拉取 attestation、谁执行 mint/forward、最终 recipient/dex 是谁 | 固定环境/合约版本清单、参数绑定、事件到 HyperCore 账务证据 |
| 出金与退款 | 用户签 HyperCore 出金；平台仅对其实际控制的资产执行获授权退款 | 退款地址的用户授权、二次筛查、双人审批、唯一付款记录 |
| PerpDock | 交易代理、builder 费授权、用户主签名、资金转移权限分别界定 | 方法级签名权限清单和负向测试，不凭“API wallet”名称推定安全 |

**推荐 MVP 默认边界：** 用户保有 HL 主钱包；Tron 收款与兑换尽量使用已核准、可对账的现有供应商；本方只做意图、报价、风险决策、编排和证据链。任何本方/第三方暂时控制资金的跳点如实披露，单独限额。优先复用官方合约；若必须新增合约或自管签名器，外部安全评审及热钱包政策进入关键路径。

中间资金虽然最终到用户钱包，仍可能存在托管、交易对手、履约、冻结与破产风险；具体法律定性由相关法域律师结合实际控制能力确认。“不经过交易所账户”只能描述实际账户路径，不能据此推出没有第三方控制。

## 三、核心威胁模型

| 威胁/错误 | 可造成的后果 | 必须实现的控制 |
|---|---|---|
| API 被盗、租户越权、Webhook 伪造 | 改地址、假到账、重复支出 | 租户隔离、服务端授权、签名 Webhook+时间窗+事件ID、出账独立鉴权、密钥轮换 |
| 前端/依赖被篡改，地址投毒 | 用户签错收款地址或恶意授权 | 交易预览、地址校验和/格式验证、目的链/资产/合约白名单、CSP与发布审批 |
| Tron 假代币/错误链、仅广播成功 | 收到无价值资产或未真实到账即垫付 | 原生 USDT 合约 allowlist、最小整数精度、solidified 成功执行与转账事件双验证 |
| 报价过期、低额/多额/迟到付款 | 隐性亏损、错付、用户争议 | 明确有效期与容差、重报价征得用户接受、独立异常状态、拒绝静默更改最小到账 |
| 重复事件、链回滚、worker 崩溃 | 重复记账/出账、状态丢失 | 幂等 intent/transfer ID、事务性 outbox、持久化尝试记录、唯一约束、可重放索引 |
| RPC 说谎/索引滞后、供应商假完成 | 错把 pending 当终态 | 关键状态多源核对；链事件和目标记账为资金证据，供应商状态仅佐证 |
| EIP 授权参数未绑定、nonce 重放 | 资金重定向或重复授权 | nonce、recipient、amount、chain/domain、hook、maxFee、有效期绑定；模拟与负向测试 |
| 库存耗尽、USDT/USDC 脱锚 | 无法交付承诺金额、损失扩大 | 报价前库存预留、资产/供应商集中度限额、保守滑点、暂停新报价及及时退款决策 |
| 热钱包/管理员被盗 | 资金损失和批量改路由 | HSM/MPC或等效隔离、最小权限、热余额封顶、提现地址 allowlist、关键变更双人复核 |
| AI 客服越权 | 泄露信息、擅自退款/交易、错误承诺 | 客服只读；退款/交易无自动执行权限；人工审批与审计；禁收种子和私钥 |
| PerpDock 交易代理泄漏 | 即便不能提现也可能用恶意交易损失本金 | 代理隔离、限制支持市场/订单、用户撤销入口、熔断、风险披露，不承诺自动止损必成交 |

Tron 官方说明广播成功不代表执行或最终确认；资金确认应读取 solidified 状态和最终执行结果。[Tron Transactions](https://developers.tron.network/reference/transactions)；[Tron 共识说明](https://developers.tron.network/docs/concensus)

## 四、资金状态与异常处置矩阵

实现多腿状态机，不能只有 pending/success/failed。推荐主状态：CREATED → QUOTED → AWAITING_SOURCE → SOURCE_CONFIRMED → RISK_CLEARED → SWAP_SETTLED → CCTP_BURNED → CCTP_MINTED → CORE_CREDITED → COMPLETED。REFUND_PENDING/REFUNDED、MANUAL_REVIEW、RECOVERY_REQUIRED 与 EXPIRED 单独记录。订单过期不等于链上迟到付款消失。

| 异常位置 | 能否自动重试 | 处置与用户展示 | 必备资金证据 |
|---|---|---|---|
| 已报价未付款，报价过期 | 可重新报价 | “报价已过期”；新报价不得复用旧授权 | 报价版本、有效期、用户确认 |
| Tron 广播成功但未 solidified/执行失败 | 查状态；不得先垫付 | “等待确认/转账失败” | 原 txID、receipt、固化状态、正确 token 事件 |
| 迟付、少付、多付、拆分付款 | 不自动按旧价执行 | 定义补款/重报价/退多余款路径 | 逐笔 transfer → intent 映射 |
| 收到资产后 KYT 命中 | 不自动转下一腿，也不自动原路退款 | “审核中”；授权人员决定持有、退还或报告 | 命中理由与模型版本、人工决定、适用规则 |
| 兑换失败且未花费资产 | 可在用户约束内换供应商 | 保留原 minOut/费用上限，否则重报价 | 未花费余额、报价、取消结果 |
| 兑换结果未知/供应商超时 | 只查询与核对，不再次付款 | “处理中”；转人工 | 供应商订单号、source tx、余额与流水 |
| burn 已确认，attestation 暂无 | 可重取 attestation | “跨链处理中”；不启动第二次 burn | burn tx、message hash、domain、原金额 |
| mint 已成功但 forward 未完成 | 仅按确证路径补执行 | “已到目标链，等待保证金入账” | mint/forward 事件及中间余额 |
| 批次交易成功，某用户被 skip | 按该条目原因修复 | 该用户仍 pending/failed | 每条事件/nonce状态，不能只看 tx.status |
| HyperCore 已记账，但 Webhook 丢失 | 可重发通知，不可重付款 | “已到账” | 用户/dex/金额/事件对应关系；不能只看余额增量 |
| 链路出现矛盾或账不平 | 停止该资金腿自动出账 | “需人工处理” | 原始数据保全、所有尝试记录、对账差异 |
| 用户要求取消但已有不可逆 burn/入账 | 不保证即时原路撤销 | 如实显示可操作步骤；退款是另笔资产流 | 每腿可撤销性与费用、用户新授权 |
| 原退款地址来自交易所/合约 | 不自动退 sender | 核验可收款地址并取得用户证明/授权 | 地址所有权/账户归属、白名单变更与复核 |

原则：重试状态查询和重复通知应安全；任何链上付出都需要先确认“之前未付或可幂等执行”。**超时、状态矛盾或未知结果不能直接退款重付，否则原转账晚到会形成双重付款。** 订单取消不能撤销已确认链上交易。**HyperEVM 钱包收到 USDC 不等于 HyperCore perps 已有可用保证金；只有指定用户、指定账户的目标入账证明可让订单进入 COMPLETED。** 账务应记录资产原币数量；收入、gas、供应商费用、库存调拨、用户应付款分科目，不以 USDT=USDC 永远 1:1 抵销。

## 五、合规/KYT：提交法律与合规负责人的问题

以下是待决策事项，不能理解为已要求所有地区一律 KYC，也不能推定钱包接口无需监管。

- 主体及目标用户法域分别是什么？提供兑换、代收、转账、衍生品入口、招揽或交易代理各自是否触发许可或限制？钱包合作方与技术提供方义务如何划分？
- 现有 KYB 的主体、业务范围、资金用途、受益人、量级和地域是否覆盖新 HL 目的地与永续交易相关流量？哪些变更需补充尽调或重签合同？
- 谁承担终端用户识别、制裁筛查、持续监控、Travel Rule（如适用）、可疑活动报告及记录保存？供应商合约是否实际承接这些工作，谁监督、审计和处理遗漏？
- “来源地址/目标地址没有命中”是否足够？地址关联、间接暴露、诈骗盗币、账户归属、受益所有人、地域和异常速度如何纳入基于风险的审核？如何处理尘埃污染和误报申诉？
- 风险决定应在何时重查？建议至少在接单前、收款后、出账前，并在名单变更/高风险事件时重评。KYT 服务不可用时新资金流默认暂缓，已在途资金的处理另按审核流程。
- 命中后能否冻结/持有/退回资产、能否向客户告知、必须向谁报告？退款也可能是受限制的资金移动，不能预设“总可原路退回”。
- HL、Circle、兑换方各自适用条款与地区限制是否覆盖实际服务？本次官方 HL terms 页面可打开但无法提取正文，不能引用二手站点的国家列表替代律师审核。上线门槛应保存当时官方条款快照并确认限制配置。[HL Terms 官方入口](https://app.hyperliquid.xyz/terms)
- 钱包地址、身份、IP、交易记录如何合法处理和跨境共享？最低必要采集、访问权限、保留期限与用户权利如何实现？
- PerpDock 费用展示、利益冲突、杠杆风险、营销、适当性和投诉机制是否需额外控制？“合规责任外包”不能作为销售承诺。

可给法务作起点的官方监管材料：OFAC 的虚拟资产指南强调按业务风险建立制裁合规程序；具体适用性及最新名单/规则仍由法务确认，不因接入 Circle/HL 自动满足。[OFAC 官方指南](https://ofac.treasury.gov/system/files/126/virtual_currency_guidance_brochure.pdf)

## 六、必要验证与质量门槛

### 集成/回归清单

1. 地址/资产：Tron Base58/hex、EVM checksum、主测试网混淆、错误 USDT/USDC 合约、原生币与桥包装币、整数精度/小数截断、dust、零值、最大值。
2. 报价/收款：过期临界点、用户拒签、广播后关页、迟到/重复/少付/多付/拆付、gas/energy 不足、非预期发送人、两租户同额同时入金。
3. 签名：篡改 recipient/domain/dex/hook/fee/amount、过期/未生效、nonce 复用、错链、错版本、重复批次、部分 skip、用户授权撤销/余额变化。
4. 结算：从 Tron 成功 transfer 到目标 HyperCore 指定用户的完整链路；新用户/现有用户；perps/spot 区分；不以 HyperEVM 到账代替完成。
5. 恢复：worker 在每个不可逆提交前后崩溃；RPC 断连、供应商先成功后超时、重复乱序 Webhook；CCTP attestation 慢、mint 后 forward 失败；链索引回放；双节点数据冲突。
6. 风控：KYT unavailable/命中/误报/人工放行、名单更新、限额突破、供应商停用、库存不足、稳定币偏离阈值、违规目的地、退款地址变更。
7. 账务：每订单资金流和账务分录守恒；“源扣一笔、目标只能到账一次”；每日资产数量及应付款核对；退款和收入不重复计提。
8. 运维：数据库备份恢复、签名器故障切换、密钥轮换、撤销凭证、熔断、在途单恢复、租户隔离、告警到人、客服查询完整证据。
9. PerpDock（另立阶段）：撤单/改单/部分成交/订单状态未知、WebSocket 丢包补快照、代理撤销/过期、nonce 并发、builder授权取消、费用上限、reduce-only/最小数量、风险提示与强平记录。

API wallet 注销/过期后 nonce 状态可能被清除，应创建新代理地址，避免复用；这是官方明确的重放风险。交易代理按用户/进程隔离，不能跨租户共享密钥。[HL Nonces and API wallets](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/nonces-and-api-wallets)

Builder 费需要用户主钱包授权最高费率，用户可撤销；分成 70/30 是本方与合作方的商业/账务设计，不是协议自动保证。[HL Builder codes](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/builder-codes)

### 放行门槛（建议）

- G0 研究通过：完成现有系统能力清单、路线 PoC、真实可执行报价和资金控制图；没有这些证据只能估工程量，不能承诺 2–4 周上线。
- G1 设计通过：研发/资金/安全/合规签署路线、可逆性、权限及失败责任；无未决 P0（错付、重复付、任意提款、账务不可恢复）。涉及新合约或自管资金须独立评审。
- G2 测试通过：上述关键负向场景、账务守恒、重放恢复全部通过；严重/高危安全问题清零；SLO 与熔断指标有数据。
- G3 小额生产灰度：必须由业务负责人确定真实资金额度与授权；单合作方、白名单、单路线、严格单笔/日总额/在途余额上限、工作时间有人值守；至少跑通退款与故障恢复样本。
- G4 扩大流量：连续观察窗口内无未解释资金差额，无重复支出，无 P0/P1 未关闭；满足成功率与支持能力；按用户数、金额、供应商分步扩容，不能只按请求比例扩容。

任何错收款人、重复出账、资金差额、未知签名、严重漏洞立即阻断新增资金流。小额灰度阈值应由可承受损失和库存确定，本文不虚构企业可承受风险。

## 七、运维指标、灰度与事故预案

以下数字是拟议内部目标，需用 PoC 和供应商能力校准后成为正式 SLO；不代表 HL/Tron/Circle 的 SLA。

| 指标 | 建议目标及口径 |
|---|---|
| 报价/订单/状态 API | 自有服务月可用性 99.9%；有效请求且依赖健康时，报价 p95 ≤ 3 秒、状态 p95 ≤ 500 ms；独立展示依赖失败 |
| 资金安全 | 每笔到账可证明；错付/重复付为零容忍门槛；账务差额即时告警，不能以总体成功率稀释 |
| 入金完成率 | 按已确认收款 cohort 统计，建议在其报价声明的时间窗内 ≥99%；人工审核、退款和失败单单独公开，不从分母悄悄删去 |
| 到账时长 | 先测逐段 p50/p95/p99；展示源链确认、换汇、attestation、HyperCore记账四段。暂无全程实测，不承诺“秒到账” |
| 状态一致性 | 关键终态发现后 60 秒内让用户可查询；Webhook 最终送达与重试状态可见 |
| 事故响应 | 高危资金事件 5 分钟内告警、15 分钟内责任人接手；团队不能满足时仅开放有值守的灰度窗口 |
| 对账/恢复 | 持续逐笔对账+每日总账；资金指令和账务记录 RPO=0 为设计目标（提交前持久化），核心状态查询 RTO≤1小时为演练目标 |

**事故流程：** 值班确认 → 按供应商/链/资产/租户熔断新单 → 保留只读查询和必要恢复 worker → 快照在途资金与签名/交易证据 → 安全、资金、合规判断哪一腿能推进 → 以订单台账逐笔恢复/退还 → 更新用户状态 → 双人核对账务 → 事故复盘后渐进重开。绝不因全局暂停将所有订单标 failed 后重新付款。

**按事故类别预案：**

- 供应商/链停摆：停新报价，清点已收款和未交付，按原协议及真实状态决定等待/退款；任何替代路线要保持用户授权的资产与最低到账。
- 热钱包或签名密钥疑似泄露：撤销 API/代理授权、停签名器、封出账、新密钥切换；转移本方资金需走既定授权，不扩大对用户资金权限。
- 稳定币偏离或流动性缺口：停止固定价报价和垫资，披露重新报价；资金部门计算最大敞口并补库存或关闭路线。
- 前端/供应链篡改：撤回受影响版本、停止交易入口、核验服务端预期与实际 calldata，识别受影响用户及已签授权。
- KYT/制裁事件：合规接管，隔离证据与访问，按法律确认流程处理；客服不得承诺即时退款或提供绕过措施。

## 八、建议优先级与未解决阻断

P0：实际 Tron→原生 USDC 供应方能力、资金控制/破产风险、目标 HyperCore 入账 PoC、全链路幂等账务、签名绑定、防错地址、KYT及法域责任、故障资金恢复。

P1：双 RPC、多供应商切换、用户退款自助、供应商/资产库存告警、结构化客服；必须在放量前补齐，不为上线日期削弱资金正确性。

后置：PerpDock、自动交易、高杠杆推荐、AI 自动处置工单或退款。PerpDock 的交易事故和监管暴露需独立预算、值班和安全评审，不能视作入金通道的小功能。

最终建议：先拿到“Tron 实际收款 → 可控换汇 → CCTP → 指定 HyperCore perps 账户 → 独立到账证据”的验证报告，再冻结 MVP 与排期。商业意向数量可以触发投入研究，不能单独触发生产上线。
